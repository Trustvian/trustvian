## Objective

is ready to produce `v0.9.0`.

## Release-gate philosophy

- **Evidence over status.** A roadmap row saying DONE is a claim to verify,
  not evidence. Every capability is re-proven from implementation, an
  executed test or command, and documentation — no row passes on
  documentation alone.
- **Corrections, not features.** This task may fix bugs, test gaps,
  documentation errors, security hardening, release automation, and
  compatibility problems. Anything needing new capability is filed as a
  follow-up and blocks the release rather than being smuggled in.
- **Severity is not negotiable to ship.** A finding is classified by what it
  would do to a user, before deciding whether to fix it.
- **Re-run after fixing.** The decision rests on results gathered after the
  last corrective change, never before it.
- **Nothing outward.** No tag, release, image push, signature, or package
  publication happens in this task.

## Scope

1. Independent verification of tasks 039–044.
2. The full local gate set: format, vet, tests, race, module verification,
   vulnerability scans, for all three modules.
3. PostgreSQL integration, stress, restart durability, backup, restore,
   behavioral recovery, upgrade, and the recovery drill.
4. Release dry-run, checksum verification, the container matrix, the image
   scan, and SBOM content.
5. Audits: public API, CLI, configuration, workflows (least privilege,
   release failure semantics), security documentation, resource safety,
   static and secret hygiene, dependencies, Go and PostgreSQL version
   policy, licensing, performance of the v0.9 hot-path change.
6. Documentation: README (evergreen, commands execute), internal links,
   project spec, architecture, operations, CHANGELOG `Unreleased`.
7. The three release-hygiene items 044 left unassigned: security disclosure
   process, issue templates, production examples.
8. The OSS/Enterprise boundary: v0.9 must work standalone, without pulling
   Control concerns into OSS.

## Non-Goals

No new behavioral capability or detector, numeric baselines, MCP security,
runtime provenance, inventory, investigation, Control Plane, Kubernetes, Helm,
or `v1.0` work. No redesign of stable public API without a concrete defect. No
performance thresholds invented after seeing results. No `v0.9.0` tag, GitHub
Release, image push, signature, or package publication. No conversion of
`Unreleased` into a `v0.9.0` section — the release guide does that at tag time.

## Audits

**Public surface.** Every exported Go identifier, CLI option, configuration
field, and environment variable added since `v0.8.0` — intentionally public,
stable name, documented, could it be internal, compatibility debt.

**Security.** SECURITY.md against real properties (behavioral state,
credentials, configuration secrets, webhooks, supply chain, backups, restore
integrity, health exposure, metric privacy); a vulnerability-reporting path;
secret hygiene across current files; workflow permissions; reachable
`panic`/`log.Fatal`/`os.Exit` on runtime paths.

**Operational.** Liveness never proxies dependency health; readiness never
falls back to memory; shutdown bounded and idempotent; every long-lived
resource classified bounded / intentionally unbounded / externally owned.

**Documentation.** A new user can find accurate install, quick start, SDK,
CLI, configuration, policy, storage, PostgreSQL, Compose, health,
observability, backup, restore, upgrade, security, and release-verification
material; README commands execute; no broken internal link; no claim that
`v0.9.0` exists.

**Compatibility.** Go version agreement across `go.mod`, CI, Dockerfile, and
docs; PostgreSQL tested-versus-supported guidance; configuration additions
backward compatible; upgrade from `v0.8.0` and rollback claims matching the
schema-version rules.

**Release artifacts.** The advertised binary and container matrices all
build; checksums verify; the release workflow's event trigger, SemVer and
commit validation, gate re-run, ordering, and permissions; what a partial
failure leaves behind and how a maintainer recovers.

## Release decision rules

| Condition | Decision |
|---|---|
| Any BLOCKER unresolved | **NOT RELEASE READY** |
| Any HIGH unresolved | **NOT RELEASE READY** |
| A MEDIUM that contradicts a documented `v0.9` contract | **NOT RELEASE READY** until fixed or the contract is corrected |
| Other MEDIUM / LOW | May be deferred, each with a written rationale |
| A finding that needs new capability | Follow-up task filed; **NOT RELEASE READY** if it blocks a v0.9 contract |
| Any gate result gathered before the last corrective change | Not admissible; re-run |

Severity guide: **BLOCKER** — a documented guarantee is false, a secret or
data-loss path ships, or the release cannot be produced. **HIGH** — a
supported workflow is broken for users (a README command fails, an advertised
target does not build, a reachable vulnerability). **MEDIUM** — a documented
detail is wrong or a proof is missing without the guarantee being false.
**LOW** — hygiene, clarity, or future-proofing.
