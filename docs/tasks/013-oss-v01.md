# 013 — OSS v0.1 Release Gate

**Milestone:** v0.1 · **Depends on:**
[001](001-feature-model.md)–[007](007-decision.md),
[010](010-examples.md)–[012](012-security-tests.md) · **Blocks:**
v0.2 (start it, or design it in more depth, only once v0.1 is real)

## Objective

Not new functionality — a checklist and gate tying every other `v0.1`
task together into an actual tagged, minimally-meaningful public
release. This task's deliverable is a verified checklist and a
release, not code.

## Why

The roadmap principle "real-world validation before enterprise
features" only means something once there's something real to
validate — a tagged `v0.1` is the first point external users can
depend on a specific, stable snapshot rather than a moving `develop`
branch.

## Scope

- Verify every task 001–007, 010–012 individually meets its own
  acceptance criteria (this task does not re-derive them — it checks
  the box each already defined).
- Verify the full existing baseline still holds after all of v0.1's
  changes land together, not just individually: `go build ./...`,
  `go vet ./...`, `go test -race ./...`, `gofmt -l .` all clean; `go
  mod tidy` produces no diff (no accidental new dependency snuck in
  across the whole milestone).
- Re-run the documentation consistency check established during the
  prior architecture-hardening pass (link/anchor checker across every
  `.md` file; grep for stale package paths, old function signatures,
  "core depends on X" phrasing) against the full `v0.1` diff, not just
  each task's own doc updates in isolation — cross-task inconsistency
  (e.g. 001 renaming something 006's docs still reference) is exactly
  what an isolated per-task check would miss.
- Confirm `examples/` ([010](010-examples.md)) runs against the exact
  code being tagged, not an earlier snapshot.
- Decide and document the actual version-compatibility promise: what,
  specifically, `v0.1` commits to keeping stable going forward (the
  `Event`/`Result` public shapes, at minimum — decide the precise
  scope during this task, informed by what 001–007 actually changed).
- Tag the release.

## Non-Goals

- No feature work of any kind — if this task discovers a gap, it
  either blocks on the relevant 001–012 task being finished properly,
  or gets explicitly deferred to a documented follow-up, never
  "quickly patched" as part of the gate itself.
- No CI/CD pipeline build-out — verifying the checks pass is this
  task's job; automating that verification to run on every future
  push is separately-justified future work (already named as such in
  [ROADMAP.md](../ROADMAP.md)'s planned bucket).

## Technical Requirements

N/A — this is a verification and release task, not an implementation
one.

## Tests

- The full existing test suite, run fresh, not from cache:
  `go test ./... -race -count=1`.

## Benchmarks

- The full benchmark suite, run fresh, with results recorded in
  [PERFORMANCE.md](../PERFORMANCE.md) as the "as of v0.1" baseline —
  future performance work has something concrete to compare against.

## Documentation

- [ROADMAP.md](../ROADMAP.md): move the "Current status" section's
  content to reflect `v0.1` as shipped; `v0.2` becomes the new "next
  up."
- A `CHANGELOG.md` (new) or release notes, summarizing what `v0.1`
  actually contains — this is the first point such a document earns
  its keep (before this, everything was pre-release iteration on a
  single evolving `develop` branch).

## Acceptance Criteria

- Every dependency task (001–007, 010–012) independently verified
  complete against its own acceptance criteria.
- `go build`/`go vet`/`go test -race`/`gofmt -l`/`go mod tidy` all
  clean on the exact commit being tagged.
- The full-repository documentation consistency check passes with zero
  findings.
- `examples/` runs successfully against the tagged commit.
- A version tag exists, with release notes describing the public API
  compatibility commitment.
